# Simulation and Observation Display Separation

## Purpose
Produce a display specification that keeps observed values, derived estimates, and scenario outputs distinguishable when they appear on the same scene or chart. It makes comparison conditions and uncertainty visible without claiming that a model accurately represents the physical system.

## Inputs to collect
1. **Viewer task** — what comparison or explanation the display supports; prevents decoration from hiding a decision boundary. Default: compare supplied observations with a scenario for exploratory discussion.
2. **Data streams and provenance** — source identifiers and whether each value is observed, derived, or simulated; determines label meaning. Default: none; unidentified streams remain unclassified and cannot be labeled measured.
3. **Time definitions** — observation time, processing time, simulation time, and forecast horizon if applicable; prevents unlike intervals being compared. Default: unknown, displayed explicitly.
4. **Spatial and measurement definitions** — entity, coordinate basis, units, aggregation, and reference conditions; establishes comparability. Default: unknown; do not calculate differences until resolved.
5. **Model and scenario metadata** — model revision, assumptions, parameter changes, and scenario identifier; separates exploratory settings from observed conditions. Default: metadata missing, scenario interpretation limited.
6. **Display capabilities** — static chart, interactive scene, accessible text alternative, export format; sets implementable behaviors. Default: static annotated diagram specification.
7. **Uncertainty evidence** — supplied intervals, model limitations, missing observations, and review status; bounds interpretation. Default: no quantified uncertainty claim.

If a required input is missing and has no safe default, ask in one message with at most 3 questions.

## Procedure
1. Identify the smallest displayed quantity whose origin can be stated unambiguously. Split blended streams into their observed and modeled components before choosing visual encodings.
2. Write an origin record for each quantity: source, transformation, model or scenario revision when applicable, represented time, and location or entity. Preserve missing metadata as an explicit gap.
3. ⚠️ Compare the measurement definitions before planning overlays or difference views. Mark mismatched time intervals, aggregation, spatial extents, or units as not directly comparable instead of subtracting plausible-looking numbers.
4. Assign persistent origin labels such as observed, estimated, and scenario. Pair those words with distinct line styles, symbols, or surface patterns so origin remains clear without color or animation.
5. Specify how the viewer enters and leaves a scenario. Display its assumptions and represented time near the view; preserve the actual observation label when controls change hypothetical parameters.
6. Define missing and unavailable states separately from low or zero values. A missing sensor sample must not become a simulated replacement that still looks measured.
7. Design comparison rules for each requested view. Permit a difference view only when definitions align; label it as a comparison to supplied observations rather than proof of model accuracy.
8. Specify uncertainty presentation using supplied evidence. Show provided bounds with their stated meaning; if no bounds exist, state that uncertainty has not been quantified instead of inventing a range.
9. Create a representative display-state table including observation-only, scenario-active, incompatible-comparison, and missing-input states. Record what each state labels, hides, or prevents the viewer from inferring.
10. Check a screenshot or export against the specification if available. Otherwise deliver an explicit inspection checklist and label verification pending; do not claim that a dashboard has been built or tested.

## Decision rules
- IF a value is generated by a model using real measurements THEN label it as a derived estimate or model output BECAUSE measured inputs do not make the result a direct observation.
- IF a scenario parameter changes THEN update the scenario identity and assumption caption BECAUSE otherwise an old interpretation can remain attached to new results.
- IF observed and simulated values represent different time windows THEN suppress a direct difference or require alignment BECAUSE a numerical gap would combine model difference with time mismatch.
- IF a missing observation is filled by an estimate THEN retain the missing-observation state alongside the estimate BECAUSE replacement should not erase the evidence gap.
- IF uncertainty bounds are unavailable THEN state that limitation BECAUSE visual precision does not establish quantified confidence.

## Output template
```text
Viewer task: <one sentence>
Origin ledger: <up to 8 quantities>
Quantity | Origin | Source or scenario | Time and entity | Comparison limit
Encoding: <one line per origin class>
Display states: <up to 6 rows>
State | Visible label | Permitted comparison | Interpretation blocked
Scenario and export rules: <up to 4 rules>
Uncertainty note: <up to 3 sentences>
Verification: <performed or pending, evidence and next check>
```

## Quality checklist
- [ ] Every quantity has an origin classification or an explicit unknown state.
- [ ] Derived estimates are not labeled direct observations.
- [ ] Time, entity, units, and aggregation are checked before comparison.
- [ ] Origin remains visible without color, motion, or a hidden tooltip.
- [ ] Missing samples remain distinct from numeric zero.
- [ ] Scenario identity and changed assumptions survive static export.
- [ ] Uncertainty language is supported by supplied evidence.
- [ ] Verification distinguishes a proposed design from an inspected implementation.

## Anti-patterns
- **One seamless truth layer:** A scene blends sensor values and model results without origin labels. Fix: preserve per-quantity origin cues.
- **Precision theater:** Decimal places imply an accurate model. Fix: state measurement definitions and uncertainty evidence separately from formatting.
- **Time collapse:** A future scenario is compared with an unrelated observation period. Fix: align periods or label comparison unavailable.
- **Silent imputation:** An estimated replacement appears as a sensor reading. Fix: show both the missing observation and replacement origin.
- **Detached export:** A screenshot loses scenario assumptions. Fix: include scenario identity, represented time, and a compact legend in the export.

## Worked example
**Input:**
> Fictional team Alder compares a room occupancy observation of 8 people for interval A with scenario S predicting 12 people for interval B. S assumes an extra meeting, which did not occur in A. Both counts refer to the same room, but the intervals differ. No uncertainty range or dashboard image is supplied.

**Output:**
```text
Viewer task: Explain observed occupancy and an exploratory meeting scenario without implying a validated prediction.
Origin ledger:
Quantity | Origin | Source or scenario | Time and entity | Comparison limit
Room count 8 | Observed | Supplied observation | Interval A, same room | Not aligned with B
Room count 12 | Scenario | S, extra meeting assumption | Interval B, same room | Not a measurement or accuracy result
Encoding: Observed = labeled solid marker; scenario = labeled outlined marker with the S caption.
Display states:
State | Visible label | Permitted comparison | Interpretation blocked
Observation only | Observed, interval A | Inspect supplied count | Current occupancy claim
Scenario active | Scenario S, interval B, extra meeting | View separately beside A | Model accuracy conclusion
Incompatible comparison | Different intervals | No direct residual | Treating the gap as prediction error
Missing observation | Observation unavailable | Scenario inspection only | Treating a prediction as a measured replacement
Scenario and export rules: Retain interval labels and S assumptions in screenshots. Changing meeting assumptions creates an updated scenario caption. Keep observation A unchanged.
Uncertainty note: No quantified uncertainty was supplied. Scenario output does not establish actual occupancy in B.
Verification: Pending visual inspection; no dashboard image was supplied. Check that a standalone screenshot retains origin and interval labels.
```

**Bad output:**
“The twin shows 12 people now and the model overpredicts by 4.”
This presents a hypothetical value as current observation and treats different intervals as a valid error comparison.

## Edge cases
- **Mixed spatial resolutions:** Label each quantity's spatial extent and disable point-to-region difference views until a justified aggregation is supplied.
- **Several model revisions:** Keep revision identifiers visible in comparison views and avoid combining outputs under one undifferentiated model label.
- **Observation corrections:** Retain correction provenance and identify affected comparison states rather than silently treating revised measurements as original readings.
- **Safety-critical request:** Stop short of control recommendations or certification; request the applicable operational context and qualified review before the visualization informs consequential action.

## Test case
**Input:**
> Fictional team Elm wants a single smooth occupancy heatmap. One zone has measured counts, another has model-filled values after its sensor stopped, and a third shows a proposed event scenario. The team supplies no uncertainty bounds.

**Assertions:**
1. The three zones remain distinguishable by persistent origin labels and noncolor cues.
2. The model-filled zone retains its missing-observation status.
3. The event scenario is identified as hypothetical rather than observed occupancy.
4. No uncertainty interval is invented.
5. The output specifies an export interpretation check without claiming an implementation was tested.
